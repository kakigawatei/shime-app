## 4. Phase2の機能設計（2）：双方向の突合せ・差異チェック（最重要）

### 4-1. 設計方針

「どちらかに偏らず、両方の情報を集約しながら差異がないかを確認」＝**シートを正としない・締めアプリの入力を正としない**。両者を同じ画面に並べ、**差があれば人に気づかせる**ところまでをアプリの責務とし、**最終的にどちらが正しいかの判断・修正は人（masa／会計転記の担当者）が行う**運用にする（自動でどちらかに書き換える機能は持たせない）。

### 4-2. 突合せの時間軸（§1-1の時間差を反映した現実的な設計）

会計台帳正本は毎朝6時のGAS同期でしか更新されないため、**「今日締めた数字」を「今日のうちに」台帳と突き合わせることはできない**。したがって突合せは常に**「過去の営業日」に対して行う**設計とする。

```
7/31 営業終了 → 締めアプリに①②③を入力（shime_closingRecordsに保存・即座に暫定サマリへ反映）
        ↓
8/1  朝6:00  会計台帳側でsyncLedger実行（人の転記＋ビルドが間に合っていれば7/31分がシートに載る）
        ↓
8/1  以降  締めアプリの「突合せ」画面で「7/31の柿川亭」を開くと、
           shime_closingRecordsの入力値 と gvizで取得した台帳の7/31行 を並べて比較できる
```

- 突合せ画面には「まだ台帳に反映されていません（syncLedger未着 or 転記待ち）」という**третий状態**を必ず用意する（シート側にその日付の行が無い＝差異ではなく「未到着」として扱い、赤い警告にはしない）。
- 何日前まで遡って突き合わせるかはUIで期間指定できるようにし（直近7日・今月など）、未確定の突合せが溜まっていれば「◯件 未確認」のバッジをホームに出す。

### 4-4. 差異検出ルール（具体設計）

各項目（券売機売上／anydeli売上／クーポン売上／通販その他／売上合計／推定来店客数）ごとに以下を計算する。

```
diff = shime値 - joe台帳値
diffAbs = abs(diff)
diffPct = joe台帳値 != 0 ? diffAbs / abs(joe台帳値) * 100 : (shime値 != 0 ? 100 : 0)

status =
  diffAbs == 0                          → "match"（✓ 一致）
  diffAbs <= 閾値_軽微円 (既定¥100)      → "minor"（△ 軽微・自動では警告表示しない、内訳に小さく表示のみ）
  diffAbs > 閾値_軽微円 かつ
    (diffAbs >= 閾値_警告円(既定¥500) または diffPct >= 閾値_警告%(既定1%)) → "warn"（⚠ 要確認）
  joe台帳側にその日の行が存在しない        → "pending"（⏳ 台帳未反映）
```

- 閾値（`閾値_軽微円` `閾値_警告円` `閾値_警告%`）は `shime_appConfig` に持たせ、券売機の端数処理・現金過不足の範囲内で誤警告が出過ぎないようmasaと合わせて初期値を調整する（§8質問）。
- 客数（`estimatedCustomers`）はanydeli換算・クーポン換算の単価が変わると連動してズレるため、単価不一致が疑われる場合（§8質問1の再確認結果次第）は客数の差異理由を「単価不一致の可能性」として注記できるようにする。
- 1項目でも`warn`があれば、その営業日の行全体に⚠バッジを付け、ホームの「◯件 未確認の差異」カウントに含める。
- 「確認済みにする」ボタンで`ledgerCompare.acknowledgedBy` `acknowledgedAt` `note`を記録する（**数字を書き換えるのではなく「見た」という記録**。実際の金額修正は台帳側 or 締めアプリ側どちらを直すかを人が判断し、直す作業自体はこの画面の外で行う＝アプリは検知と記録に徹する）。

### 4-5. gviz取得の防御設計（タブ名不一致・列ずれリスクへの対策）

masaのメモ・`joe`のコードコメントの両方が指摘する通り、**gvizはタブ名が一致しないと無言で先頭シートを返す**。これは会計データの突合せにおいて「違う店舗のデータを同じ店舗として比較してしまう」という一番怖い事故につながるため、Phase2では次の防御を必須とする。

1. **タブ名は`shime_appConfig`に持たせ、コード直書きにしない**（`joe`側もコード直書きのため過去に改名で追従漏れが起きた。締めアプリ側だけでも設定画面から直せるようにし、改名時の対応コストを下げる）。
2. **取得後にシート内容の"見出しセル"を検証**する。実測した通り、日次タブのA1相当セルには`"柿川亭 日次売上（2026年7月） 月次小計"`のように店舗名が入っている。取得後、この文字列に対象店舗名（例："柿川亭"）が含まれるかをチェックし、含まれなければ「タブ名が一致していない可能性があります」という明示的なエラーを出し、**古い/別店舗のデータを差異チェックに使わない**（サイレントに間違ったデータで警告を出さないことを優先する）。
3. 日付列（0列目）が`YYYY-MM-DD`にマッチしない行はスキップする（`joe`の`parseDaily`と同じ防御をそのまま踏襲）。
4. 取得失敗時・見出し検証失敗時は「前回成功時のキャッシュ」を使わず、突合せ画面には**明示的に「取得できていません」を出す**（間違った比較よりは「比較できない」を選ぶ＝安全側に倒す）。

## 6. 安全な連携方式（案A／案B・比較と推奨）

### 案A：締めアプリはFirestoreに保持し、シートは「読み取りで突合せのみ」（書き込みなし）

- `shime_closingRecords`（Firestore）が単独のソースであり続け、会計台帳側には一切書き込まない。
- gvizで読み取り、§4の突合せに使うだけ。
- **メリット**：`joe`・会計台帳の既存の挙動を100%変えない。実装対象が締めアプリ側のみで完結し、GASや権限周りの新規リスクがゼロ。過去の「シートを壊した」事故が原理的に起こり得ない（書き込み経路が存在しないため）。
- **デメリット**：数字が二重管理のまま（台帳への反映は結局、人が手で転記する既存フローに依存し続ける）。締めアプリの入力が「台帳への正式な入力」を代替することはない（あくまで検算・速報用）。

### 案B：GAS Web App（`doPost`）で新規タブ／新規列にのみ書き込む

- 会計台帳スプレッドシートに **新規タブ**（例：`🖥締めアプリ入力：柿川亭`）を追加し、GAS Web Appが`shime_closingRecords`の内容をそこに書き込む。**既存の`🍜日次：柿川亭`タブ・既存の手入力列には一切触れない**。
- masaの会計転記担当者が、新規タブに並んだ「現場からの速報値」を見ながら、正規の手入力を行う際の参考にできる（転記のダブルチェックとして機能）。
- 将来的に信頼性が確認できれば、新規タブの値を正規タブへ**人が**コピーする運用に格上げする道もあるが、**アプリが正規タブへ自動書き込みすることは本書の範囲では提案しない**（自動書き込みによる事故リスクを避けるため、あくまで「隣に置く」に留める）。
- **メリット**：会計転記の二度打ちを減らせる可能性、締めアプリ側の入力が台帳側からも見える。
- **デメリット**：GASの権限設定（サービスアカウント or OAuth）・Web Appのデプロイ・エラーハンドリング（書き込み失敗時のリトライ等）という新規の技術的負債が発生する。新規タブとはいえシートに書き込みコードが存在すること自体が「触れる経路がある」というリスク（誤ってタブ名の参照を間違えるとPhase3以降別のタブに書いてしまう可能性はゼロではない）。

### 推奨

**Phase2は案Aのみを実装する。案Bは採用可否を含めてPhase2cとして保留し、実行はmasaの明示的なGOサインが出てから着手する**（§7）。

根拠：
1. masaの狙いの核心は「入力の精度を高める」「差異に気づく」ことであり、これは**読み取り突合せだけで達成できる**。書き込みは必須要件ではない。
2. 過去にGoogleシートのタブ名・列を変えて`joe`を壊した経緯がある以上、**新規リスクを追加する判断は最小限にすべき**。案Bは「新規タブのみ」という安全設計だが、それでも書き込み経路の新設という質的に異なるリスクを持ち込む。
3. 案Aで一定期間運用し、「アプリの入力精度が十分に信頼できる」とmasaが判断できてから案Bを検討する方が、段階を踏んだ安全な進め方になる（§7のPhase2cに対応）。

## 9. masaに確認すべき質問リスト

### データの意味・入力元（Phase2a着手前に必須）
1. `🍜日次：柿川亭`シートの8・9・10列目（券売機杯数／anydeli換算人数／クーポン換算人数と推測）は、実際にその意味・その並び順で合っているか（`joe`アプリのコードはこの3列を使っていないため、本書の対応付けは未検証＝暫定）。あわせて4列目「クーポン枚数」の位置も合わせて確認したい。
2. 「券売機集計」は具体的に券売機のどの画面・どのボタンの数字を、いつ・どうやって確認しているか（レシート集計ボタン等）。締めアプリの入力欄をその実際の操作に合わせたい。
3. 「anydeli」の数字はanydeliの管理画面のどこを見て、何を転記しているか（売上・件数のどちらを主に転記しているか）。
4. anydeli換算単価（¥1,000）・クーポン1枚の単価（¥1,000）は`設定`タブに書かれている値を確認したが、**今後変わる可能性はあるか**。変わる場合、締めアプリ側（`shime_appConfig`）とシート側（`設定`タブ）を都度手動で合わせる運用でよいか。

### 既存の「差額確認」列について（重要な新規発見）
5. 実際にシートを確認したところ、`🍜日次：柿川亭`の12列目に**「差額確認」列が既に存在し、`OK`という値が入っている**ことが分かった。これは**誰が・いつ・何と何を比べて**`OK`/`NG`を付けているものか。Phase2で作る自動突合せ（§4）と役割が重複しないか、あるいは補完関係になるか、教えてほしい（場合によっては、この列の運用を締めアプリ側に一部統合できる可能性がある）。

### 連携方式・運用
6. 会計台帳スプレッドシートへの**書き込みを許可してよいか**（§6 案B）。許可する場合、「新規タブにのみ書く」という安全策で進めてよいか。当面は許可せず案Aのみでよいか。
7. 会計台帳スプレッドシートは**このまま同じID（`1cMfv...`）を使い続けるのか、月が変わるごとに新しいスプレッドシートを作る運用になる可能性があるか**（`joe`のコードには「月ごとにシートが変わる想定」というコメントと、月ごとに1行追加できる`SHEETS`配列が用意されており、将来ID自体が変わる設計になっているように見える）。変わる場合、締めアプリ側にもその都度反映が必要になるため、運用ルールを決めておきたい。
8. 「確定」の運用は誰が・いつ行うか（例：営業終了直後に店長が入力・確定するのか、翌朝masaが台帳と見比べてから確定にするのか）。本書では「確定後も編集可能」設計にしているが、実際の運用フローに合わせて調整したい。
9. 差異チェックの閾値（軽微¥100・警告¥500 or 1%、§7）はmasaの体感として妥当か。券売機の端数処理や現金過不足の通常レンジを踏まえて初期値を決めたい。
