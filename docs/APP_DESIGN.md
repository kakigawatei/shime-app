# 柿川亭×アブララボ「締めアプリ」設計書

対象店舗: 柿川亭（本店・油そば専門店）／アブララボ（油ラボ・実験店）の2店舗
利用者: masa＋社員（複数人で共有）
最終形: 営業終了後の「締め」を1つのアプリで一気通貫処理（券売機集計→anydeli集計→客数確認→仕入記録→発注）
実装方針: **段階的**。本設計書は最終形を見据えつつ、**Phase1＝発注のみ**から着手できるように詳細化する。
配信方式: インストール不要のPWA（GitHub Pages＋クライアントJS）、クラウドはmasa既存のFirebaseプロジェクト `kakigawatei-franchise` を流用（「ながおか探検録」「crowd.html」と同一プロジェクト・同一APIキー）。
関連ドキュメント: Firestoreの詳細スキーマ・セキュリティルール・業者品目マスタの叩き台は [`docs/DATA_MODEL.md`](./DATA_MODEL.md) を参照。

## 0. 前提として読んだ資料

- `docs/reference/order_sms_hokushoku.png` — ホクショク（佐藤卓氏）宛のSMS実物。パターン：「お世話になっております。／明日◯曜日／店舗名／品目 数量（複数行）／お願いいたします🙇」。品目名は「豚骨のタレ2本（内1はアブララボ）」のように**店舗内訳を1品目の中に書ける**表記と、「柿川亭のタレ1ケース」のように**店舗名を冠した別名**表記がある（表記ゆれの可能性＝要確認、質問リストに記載）。相手からの自動返信「いつもお世話になっております。ご注文承りました。お届けいたします。」も確認（アプリ側で扱う必要はない＝業者の定型自動応答）。
- `docs/reference/order_sms_mentsu.png` — めんつう宛のSMS実物。連絡先ラベルは「めんつうさんメール」だが吹き出しは緑（＝iMessageではなくSMS）なので、実チャネルはSMSで確定（masaの分類表と一致）。品目の連結が「冷凍12番150gを1と／冷凍16番太麺1と／太麺1」のように**「と」で自然文連結**される点、複数行の間に空行が入ることがある点、そして**同日に店舗を分けて追送する**運用（「あと、明日金曜日／アブララボに／太麺1／お願いいたします🙇」）を確認した。これは「1回の締め操作で、同じ業者に対して店舗ごとに複数通のメッセージを生成し得る」という設計要件に直結する（§4で反映）。
- masaの既存資産の技術パターン（`nagaoka-walk/crowd.html`）：Firestore REST APIを直接fetchで叩く構成（SDKなし）、Firebase Authはメール/パスワードでの店舗単位ログイン＋`shopOwners/{uid}`でuid→店舗IDを解決、というパターンが既に本番稼働している。締めアプリの認証設計（§5）はこれと接続可能な形にする。
- `uriage-dashboard`（愛称「番頭」＝joe）の日次シート列定義、および会計台帳（ジョー）のGAS同期の存在を前提に、Phase2以降の連携ポイントを設計する。

## 1. アプリ全体像とコンセプト

### コンセプト
**「営業が終わったら、このアプリを上から順にタップしていけば締めが終わる」**。
毎晩の「締め」は本来ひとつながりの作業（レジを閉める→客数を確認する→今日仕入れたものを記録する→明日の分を発注する）なのに、今は券売機端末・anydeliの管理画面・SMS/LINE/Messengerの手打ち・紙やスプレッドシートの台帳、と**バラバラの場所**でやっている。これを1本の画面フローにまとめ、「今日やることリスト」を消し込んでいく感覚で終わらせられるようにする。

### 一発フロー（最終形・Phase2以降で順次解放）
```
① 店舗を選ぶ（柿川亭 / アブララボ）
        ↓
② 券売機の集計を入力          … Phase2
        ↓
③ anydeliの集計を入力          … Phase2
        ↓
④ 客数を自動計算・確認         … Phase2（客数＝主食杯数＋anydeli換算＋クーポン）
        ↓
⑤ 今日の仕入（納品）を記録      … Phase3〜4
        ↓
⑥ 明日の発注を作って送る        … Phase1（★最初に実装）
        ↓
⑦ 「本日の締め、完了」          … 全ステップの完了状態を保存
```
**実装順序はこの逆から着手する**＝⑥の発注が最も定型化されていて価値が出しやすく、業者ごとにチャネルが違うという最大の技術的難所もここにある。Phase1で⑥を単独の完成度で仕上げ、Phase2で②③④を追加して「締めダッシュボード」を上から埋めていく形に統合し、Phase3で⑤と会計シート連携、Phase4で発注の自動提案（在庫連動）に進む。

### 画面には常に「今日、どこまで終わったか」が見える
締めダッシュボード（§3-2）は、上記①〜⑦の各ステップが「未着手／入力中／完了」のどれかを店舗×営業日単位で持ち、他のスタッフが見ても「もう発注は終わってる」「anydeliの入力がまだ」が一目でわかるようにする（同じ日に複数人が触っても二重発注・入力漏れを防ぐ）。

## 2. 情報設計・データモデル（概要）

Firestore（`kakigawatei-franchise`）に、既存コレクション（`shopOwners` `crowd` `announcements` 等）と衝突しないよう **`shime_` プレフィックス**を付けた新規コレクション群を追加する。詳細フィールド定義・サンプルドキュメント・セキュリティルール案は [`docs/DATA_MODEL.md`](./DATA_MODEL.md) に分離して記載する。ここでは全体構造のみ示す。

| コレクション | 役割 | Phase |
|---|---|---|
| `shime_stores` | 店舗マスタ（柿川亭／アブララボ、将来6店舗に拡張可） | 1 |
| `shime_staff` | スタッフ名簿（担当者表示用、アカウントではない） | 1 |
| `shime_suppliers` | 業者マスタ（名称・連絡チャネル・連絡先・締め時間） | 1 |
| `shime_suppliers/{id}/items` | 業者ごとの定番品目カタログ（単位・店舗内訳可否など） | 1 |
| `shime_orderTemplates` | 店舗×業者のよく使う定番セット（任意・時短用） | 1〜2 |
| `shime_orders` | 発注1件＝1メッセージ（業者・店舗・品目・生成文面・送信状態） | 1 |
| `shime_shoppingList` | 共有の買い出しチェックリスト（スーパー等・業者発注とは別枠） | 1 |
| `shime_inventory` | 品目ごとの残数・適正在庫（発注数自動提案の元データ） | 4 |
| `shime_closingRecords` | 日次の締め記録（券売機/anydeli/客数/仕入/発注の進捗と実績値） | 2〜3 |
| `shime_appConfig` | 共有PIN・機能フラグ等のアプリ全体設定 | 1 |

設計方針：
- **2店舗を横断する共有ドキュメント**（`shime_suppliers` の品目カタログ、`shime_shoppingList` など）と、**店舗ごとに分かれるドキュメント**（`shime_orders` `shime_closingRecords` は必ず `storeId` を持つ）を明確に分ける。将来6店舗に拡張する際は `shime_stores` にレコードを足すだけで済むようにし、コード側は店舗IDをハードコードしない。
- Firestoreはリアルタイムリスナー（`onSnapshot`）を使わずREST APIのポーリング/都度fetchでも実用上問題ない規模（1日数十件の書き込み）だが、「締めダッシュボードの進捗が他スタッフの画面にすぐ反映される」体験を重視する場合はPhase2で軽量なリアルタイム購読（Firestore REST の `:listen` あるいはSDK導入）を検討する、と明記するに留める（Phase1はシンプルさ優先でfetch都度取得）。

```
│   │ ──────────────────────  │   │
│   │ プレビュー（タップで直接編集可）:      │   │
│   │ ┌─────────────────────┐│   │
│   │ │お世話になっております。      ││   │
│   │ │明日土曜日                ││   │
│   │ │柿川亭                   ││   │
│   │ │太麺2                    ││   │
│   │ │お願いいたします🙇          ││   │
│   │ └─────────────────────┘│   │
│   │        [ SMSを開いて送信 ]     │   │
│   └───────────────────────┘   │
│ ▾ ホクショク（SMS）      未送信          │
│   （同様のカード。豚骨のタレ等は          │
│    「内訳」トグルで内◯はアブララボ、と付記可）│
│ ▾ 中越鶏卵（メール）     未送信          │
│   [ メールで自動送信 ]（or ワンタップmailto）│
│ ▾ 竹内農園（LINE）      未送信          │
│   [ LINEを開く（本文入り） ] [ 本文コピー ] │
│ ▾ アルベル（Messenger）  未送信          │
│   [ Messengerを開く ] [ 本文コピー ]      │
│ ▾ マルヤマ包装（LINE）    未送信          │
│   [ LINEを開く（本文入り） ] [ 本文コピー ] │
└─────────────────────────────────┘
```
ポイント：
- 業者カードはアコーディオン。**その日すでに送信済みの業者は自動的に折りたたまれ「✅送信済み」バッジ**が付く（誰が見ても今日の発注状況がわかる＝二重発注防止）。
- 品目は業者ごとの定番カタログから±ステッパーで数量指定（実物SMSの「太麺2」「豚骨のタレ2本」に相当）。数量0の品目は文面に出さない。
- **店舗内訳トグル**：「内◯はアブララボ」表記が必要な品目（豚骨のタレ等、`allowStoreSplit: true`のもの）はステッパーの下に小さく「内訳を付ける」リンクが出て、タップすると「合計2、うちアブララボ [－1＋]」の入力に切り替わる。文面生成時に「豚骨のタレ2本（内1はアブララボ）」の形に自動整形。
- **重量・番号指定品**（「冷凍12番150g」等）は品目自体をあらかじめ個別のカタログ行として登録しておく方式をMVPとする（番号や重量を都度自由入力させると誤発注の元になるため）。よく出る組み合わせを業者マスタに事前登録し、レアケースは自由入力欄で対応。
- プレビューは**必ず編集可能**。自動生成文面をそのまま送るのではなく、最終的に人間が目視確認・手直しできる状態で提示する（実物SMSでも表記ゆれが見られたため、テンプレに完全依存させない設計とする）。
- **同一業者・同日に複数店舗ぶんを別々に送る**運用（めんつうの実例：柿川亭ぶんを送った後に「あと、明日〜アブララボに〜」を追送）にも対応できるよう、店舗切替タブを変えて同じ業者カードを開けば**その業者への当日2通目**として別の`shime_orders`ドキュメントが作られる（履歴には2件別々に残る）。

## 4. 発注の送信メカニズム（チャネル別・最重要パート）

masaの業者は6社、連絡チャネルが3系統（メール／SMS／LINE・Messenger）に分かれ、**チャネルごとに自動化の限界が異なる**。iPhoneネイティブSMSの無人一斉送信は専用ゲートウェイ＋別番号が必要で非現実的、LINE/Messengerは規約上ボット的な自動送信ができない（個人アカウント運用のため）。したがって現実的なゴールは：

> **文面は全業者ぶん自動生成する。送信は「メールは自動化可」「SMSはワンタップで送信画面まで」「LINE/Messengerはワンタップ起動＋本文コピー」に振り分ける。**

### 4-1. 文面テンプレートのデータ化
実物SMSから抽出した型をテンプレートオブジェクトとしてデータ化する（`shime_suppliers` の各ドキュメントに保持、§DATA_MODEL参照）。

```
{挨拶}
明日{曜日}
{店舗名}
{品目行1}
{品目行2}
…
{結び}{絵文字}
```
- `挨拶`: 既定 `"お世話になっております。"`（業者ごとに上書き可能。実物では初回だけ「いつもお世話になっております。」等の変化もあり得るが、MVPでは固定文で統一し、必要ならプレビューで手直しする運用とする）
- `明日{曜日}`: お届け希望日から自動算出（今日／明日／明後日／日付指定を選択→「明日金曜日」のように相対＋曜日表記を自動生成。実物と完全一致するロジック）
- `品目行`: 数量>0の品目のみ、`{品目名}{数量}{単位}` を基本形とし、内訳がある場合は `{品目名}{数量}{単位}（内{内訳数}は{内訳店舗名}）` を自動組み立て。めんつうの「Aを1と／Bを1と／C」のような**文中連結の癖**は業者ごとの`itemJoiner`設定（`"改行"` or `"を◯と＋改行"`）で吸収できるようにし、初期値は「品目ごとに改行」（実物のホクショク側パターン）とする。めんつう側の「と」で繋ぐ文体は任意設定として用意するが、**プレビューで必ず人が確認する**ことで多少の型ブレは許容する設計とする。
- `結び`: 既定 `"お願いいたします"` ＋ 絵文字 `🙇`（業者ごとに変更可）

### 4-2. チャネル別の送信実装

| チャネル | 業者 | 実装 |
|---|---|---|
| **メール** | 中越鶏卵 | Phase1初期は `mailto:宛先?subject=…&body=…` のワンタップリンク（Mail.appが開き、最後の送信ボタンだけ人が押す＝半自動）。masaが完全無人化を望む場合は、Phase1後半で**GAS（Google Apps Script）の時限トリガー**が`shime_orders`（Firestore REST経由で参照）を数分おきにポーリングし、`channel:"email" & status:"queued"` の注文を`GmailApp.sendEmail`で自動送信→`status:"sent"`に更新する小さな中継スクリプトを追加する（会計台帳の朝6時GAS同期と同じ運用パターンを流用でき、Cloud Functions等の新規インフラを増やさずに済む）。**まずmailtoワンタップで始め、実運用で信頼できたら自動送信に格上げする**、の二段構えを推奨。 |
| **SMS** | めんつう、ホクショク | `sms:電話番号?&body=URLエンコード済み本文` のディープリンクをボタンに設定。タップでメッセージAppが本文入りで開き、**人が最後に送信ボタンを押す**（iOSのSMS無人送信はキャリア規制上不可のため、これが現実的な上限）。送信後、アプリ側は自動検知できないため「送信しました」の手動確認ボタンをMessagesから戻ってきた後に軽く出す（任意タップ、忘れても履歴には「開いた記録」は残る）。 |
| **LINE** | 竹内農園、マルヤマ包装 | `line://msg/text/URLエンコード済み本文` のディープリンクでLINEアプリを開き、**送信先（友だち）を選ぶ画面に本文入りで遷移**（LINE標準の「テキストを共有」動線）。人が竹内農園／マルヤマ包装のトークを選んで送信ボタンを押すだけで済む＝実質ワンタップに近い体験。スキーム非対応の端末・LINEバージョンに備え、「本文をコピー」ボタンも必ず併設し、コピー後に`line://`（トップ起動）でLINEを開くフォールバックを用意する。 |
| **Messenger** | アルベル | Messengerには本文プリフィルの安定した公開ディープリンクがないため、**「本文をコピー」＋「Messengerを開く」**の2ボタン構成を基本とする（`fb-messenger://user-thread/相手のPSID`が分かれば特定スレッドを開けるが要検証・要相手情報）。人がコピペで貼り付けて送信。 |

### 4-3. 送信後の状態管理
`shime_orders` の `status` は `draft → opened(送信画面/アプリを開いた) → sent(人が送信操作をしたとアプリ内で確認) → (将来)acknowledged`。メール自動送信のみ厳密な「実際に送られた」を機械的に保証できる。SMS/LINE/Messengerは**性質上「開いた」までしか機械的に確認できない**ため、履歴画面では「開いた時刻」を主表示にし、「送信済みですか？」の軽い確認チェックを添える程度に留める（過剰に厳密な状態管理を求めない）。

## 5. 認証・共有

社員複数人が同じ2店舗のデータを共有して使うツールであり、consumer向けアプリのような不特定多数アクセスは想定しない。段階的に強度を上げる。

### Phase1〜2：共有PIN＋匿名認証（低摩擦優先）
- Firebase **匿名認証**（`nagaoka-walk`と同じ仕組み）でFirestoreへの読み書き権限を得る。個人アカウント作成は不要。
- アプリ起動時に**共有PIN**（4〜6桁、`shime_appConfig`に保持）の入力を1回だけ求め、正しければ端末（localStorage）に記憶し以降は自動突破。PINは「誰でも入れる公開URLではない」ことを担保する程度の軽い関門（性質上、知っている人になら共有されうる前提）。
- PIN通過後、**担当者名の選択**（`shime_staff`のリストから選ぶ、もしくは自由入力）をlocalStorageに保存し、以降のすべての書き込み（発注・チェックリスト操作等）に`createdByName`として付与する。これは**セキュリティではなく記録・属人性のため**（「誰が送った発注か」を履歴で追えるようにする）。
- Firestoreセキュリティルールは「サインイン済み（匿名含む）なら`shime_`配下は読み書き可」という比較的緩いルールを許容する（社内限定URL・PINゲートの組み合わせで実運用上のリスクは低いと判断。詳細は`DATA_MODEL.md`のルール案参照）。

### Phase3以降：会計データに触れる段階での強化（検討事項として明記）
売上・会計関連の書き込み（`shime_closingRecords`、将来のGoogleシート書き込み）を扱うようになったら、`crowd.html`と同じ**店舗単位のメール/パスワードアカウント＋`shopOwners`相当のマッピング**（例：`shime_staffAccounts/{uid} → storeId`）に格上げし、Firestoreルールで「該当店舗のドキュメントしか書けない」ことをサーバ側で保証する方式への移行を検討する。この移行はPhase3着手時に改めて設計する（本書では方針のみ明記）。

### 店舗切替
ログイン＝店舗紐付けにはしない（同じ担当者が両店舗を扱うことがあるため）。**画面上部の店舗タブで都度切り替える**方式とし、直近選んでいた店舗をlocalStorageに記憶して次回起動時に復元する。

## 6. 技術構成

- **配信**: GitHub Pages（新規リポジトリ、例 `kakigawatei/shime-app`。現在のローカル`C:\Users\masat\Desktop\shime-app`はgit初期化済みでリモート未設定＝要masa作業）。
- **フロントエンド**: ビルドレスの静的HTML/CSS/バニラJS。`nagaoka-walk`/`uriage-dashboard`と同じ流儀（フレームワーク・バンドラなし、1〜数ファイル構成）で保守コストを揃える。
- **PWA化**: `manifest.webmanifest`（アイコン各サイズ、`display: standalone`）＋`sw.js`（アプリシェルのキャッシュファースト、Firestore通信はキャッシュしない）。iOSは「ホーム画面に追加」でアプリアイコンから起動できるようにする（`nagaoka-walk`のmanifest構成を流用）。
- **データ層**: Firestore REST API（`https://firestore.googleapis.com/v1/projects/kakigawatei-franchise/databases/(default)/documents/...`）に対し、SDKを使わず直接`fetch`する構成（`crowd.html`と同一パターン）。認証は匿名認証のIDトークンを`Authorization: Bearer`で付与。
- **メール自動送信（中越鶏卵）**: 前述の通りPhase1はmailtoワンタップ、必要になれば軽量GAS中継（時限トリガー＋GmailApp）を追加。新規サーバーは持たない方針を維持。
- **アイコン・ブランディング**: 「番頭（joe）」のような専任キャラクターは不要（実務ツールのため落ち着いたトーンでよい）。店舗ロゴ or シンプルな「締」の文字アイコン程度を想定（要masa相談）。
- **オフライン考慮**: 締め作業は必ずWi-Fi/電波のある店舗内で行われる想定のため、オフライン編集・後で同期のような高度な対応はPhase1では不要（将来の圏外対応はPhase4以降の検討事項とする）。

## 7. 段階的ロードマップ

### Phase1：発注MVP
**スコープ**: `shime_stores` `shime_staff` `shime_suppliers`（+items） `shime_orderTemplates` `shime_orders` `shime_shoppingList` `shime_appConfig` を実装。発注画面・業者マスタ管理画面・買い出しリスト・履歴（発注のみ）・PINゲートを実装。締めダッシュボードは骨格のみ（他ステップはグレーアウト）。
**完了条件**:
- 6社すべての業者・定番品目カタログが登録済みで、masaまたは社員が**このアプリだけで**当日ぶんの発注文面を作れる。
- 中越鶏卵はメール、めんつう／ホクショクはSMSディープリンク、竹内農園／マルヤマ包装／アルベルはLINE・Messenger起動＋コピーで、実際に1週間以上、手打ちに戻らず運用できている。
- 発注履歴が正しく残り、同じ内容の複製発注がワンタップでできる。
- 買い出しリストが複数人で同時に使えている。

### Phase2：券売機・anydeli集計＋客数
**スコープ**: `shime_closingRecords` を追加。締めダッシュボードの①〜③を実装（券売機売上・杯数、anydeli売上・換算、クーポン枚数・売上の入力→客数自動計算）。
**完了条件**: masaが今joeの日次シートに手で入れている数字を、このアプリでの入力で代替できる（並行運用1週間で数値が一致することを確認）。書き込み先はまだGoogleシートではなくFirestore（`shime_closingRecords`）のみ。

### Phase3：会計連携（シート書き込み）
**スコープ**: `shime_closingRecords`の内容を既存の「日次シート」（joeが参照する公開シート）へ書き込む経路を実装。方式はGAS Web App（`doPost`）またはSheets APIのいずれかを技術検討（本書では両案を候補として明記、選定はPhase3着手時に行う）。あわせて仕入記録（`shime_orders`の実配達確定→会計台帳との紐付け）を追加。
**完了条件**: 書き込みは**既存の手入力列を一切壊さない**ことを最優先とし、まずは新規タブ／新規列への書き込みでmasaの確認を得てから本番列に合流する、という段階を踏む（過去にGoogleシートを壊した経緯があるための安全策）。masaの明示的なGOサインが出るまで本番シートへの書き込みは行わない。

### Phase4：在庫→発注自動提案・分析
**スコープ**: `shime_inventory`（残数入力）を追加し、品目ごとの適正在庫（par level）との差分から発注数量を自動提案（人が最終確認・修正して送信、自動送信はしない）。あわせて発注頻度・コスト推移等の簡易分析を履歴画面に追加。
**完了条件**: 残数入力→提案数量が体感で「だいたい合っている」状態になり、発注作業の入力の手間がさらに減っている。
